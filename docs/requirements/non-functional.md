# Нефункціональні вимоги

Джерело: звіт `docs/Errandly.pdf`, практична робота №3 (с. 19–29). Функціональні вимоги — у [functional.md](functional.md), системні — у [system.md](system.md).

Нефункціональні вимоги (NFR) визначають, наскільки якісно Errandly виконує функції, описані в ПР2, і які обмеження діють на продукт та процес його розробки. Такі вимоги стосуються продуктивності, надійності, безпеки, зручності, процесу розробки та зовнішніх чинників (закони, умови сторонніх сервісів). Їх сформовано на основі цілей ПР1 і функціональних вимог ПР2 з урахуванням документації Google Calendar API та моделі якості ISO/IEC 25010.

Вимоги записано у формі «повинен/повинна» з кодом NFR-XXX-NN, пріоритетом (M – Must, S – Should, C – Could, W – Won't have) і посиланням на пов'язані FR; де це можливо, вказано вимірюваний критерій.

Скорочення: p95 – 95-й перцентиль часу відповіді; TLS – протокол захисту транспортного рівня; UTC – всесвітній координований час; OWASP – Open Worldwide Application Security Project; WCAG – Web Content Accessibility Guidelines; ORM – об'єктно-реляційне відображення.

## Вихідні дані, обмеження та стейкхолдери

Нефункціональні вимоги випливають з параметрів проєкту, визначених у ПР1:

| Параметр проєкту  | Значення                                                                                          | Вплив на вимоги                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Команда та строки | 6 виконавців; нефункціональні вимоги – 28 вересня – 5 жовтня; завершення розробки до 30 листопада | Пілотний рівень доступності й масштабування, пріоритет автоматизації перевірок (CI) |
| Архітектура       | Тришарова: SPA-клієнт, серверна частина, база даних                                               | NFR-MAIN-01, NFR-SEC-04                                                             |
| Зовнішні сервіси  | Google Calendar API, Gmail SMTP, GitHub                                                           | NFR-REL-02, 03; NFR-COMP-02; NFR-SEC-05; NFR-LEG-03                                 |
| Аудиторія         | Співмешканці, зокрема студенти гуртожитків Могилянки; групи 2–10 осіб                             | NFR-PERF-01, 03; NFR-USE-01, 02                                                     |
| Дані              | Облікові записи, групи, задачі, токени доступу до календаря; платежів і чутливих даних немає      | Акцент безпеки на автентифікації, правах доступу й токенах                          |

Вимоги до якості впливають на різних стейкхолдерів (ролі описано в [functional.md](functional.md#користувачі-та-стейкхолдери)):

| Стейкхолдер         | Очікування щодо якості                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Учасник групи       | Швидкий і зрозумілий інтерфейс на смартфоні, збереження даних, захист облікового запису й конфіденційності групи |
| Адміністратор групи | Надійне керування складом групи й задачами, відсутність втрати даних під час перерозподілу                       |
| Викладачка курсу    | Вимірюваність та перевірність вимог, відповідність цілям ПР1                                                     |
| Команда проєкту     | Супроводжуваність коду, автоматизоване тестування, відтворюване розгортання                                      |

## Класифікація

Вимоги згруповано за категоріями, узгодженими з характеристиками якості ISO/IEC 25010 та поділом SWEBOK на вимоги до продукту, до процесу та зовнішні вимоги.

| Код  | Категорія                                   | Характеристика ISO/IEC 25010 | Тип (SWEBOK)     |
| ---- | ------------------------------------------- | ---------------------------- | ---------------- |
| PERF | Продуктивність                              | Performance efficiency       | Продукт          |
| REL  | Надійність і доступність                    | Reliability                  | Продукт          |
| SEC  | Безпека                                     | Security                     | Продукт          |
| USE  | Зручність використання                      | Usability                    | Продукт          |
| COMP | Сумісність та інтеграція                    | Compatibility                | Продукт          |
| MAIN | Супроводжуваність                           | Maintainability              | Продукт / процес |
| DEP  | Розгортання, переносимість, масштабованість | Portability                  | Продукт          |
| PROC | Процес розробки                             | –                            | Процес           |
| LEG  | Правові та зовнішні                         | –                            | Зовнішні         |

## Перелік вимог

У колонці «FR» зазначено функціональні вимоги ПР2, до яких вони застосовуються.

Числові значення узгоджено із загальновизнаними джерелами й галузевими рекомендаціями, а де прямого стандарту немає, їх визначено як цільові показники пілотного запуску з урахуванням розміру груп (2–10 осіб). Пороги швидкодії інтерфейсу відповідають граничним часам сприйняття користувачем та метрикам Core Web Vitals. Цільова доступність і вимірювання за перцентилями спираються на практику SLO. Вимоги до паролів, токенів і транспортного захисту узгоджено з NIST SP 800-63B, NIST SP 800-52 та рекомендаціями OWASP. Повторні спроби синхронізації з календарем відповідають рекомендаціям Google Calendar API, поріг покриття тестами – практикам Google, а розмір вибірки юзабіліті-тесту – дослідженням Nielsen. Значення без зовнішнього джерела (резервне копіювання, розмір JavaScript-пакета, строки виконання фонових процесів) є експертними оцінками команди.

## Критерії прийняття (BDD-сценарії)

Для ключових нефункціональних вимог записано критерії прийняття у форматі Given–When–Then, так само, як для функціональних вимог у ПР2.

### Сценарій 1. Швидкодія списку задач (NFR-PERF-01)

```gherkin
Given у групі 10 учасників і 200 задач, з'єднання 10 Мбіт/с
When учасник відкриває список задач
Then список повністю відображається не довше ніж за 2 с (p95 за 20 вимірювань)
```

### Сценарій 2. Збій Google Calendar (NFR-REL-02)

```gherkin
Given Google Calendar API повертає помилку 503

Then задачу збережено в застосунку
And синхронізацію поставлено в чергу з повторами (до 5 спроб)

```

### Сценарій 3. Доступ до чужої групи (NFR-SEC-04)
