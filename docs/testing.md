# Тестування

Тести побудовані пірамідою (NFR-MAIN-02): найбільше unit-тестів, менше інтеграційних, найменше e2e. Одне правило перевіряється на одному рівні: чисту логіку не перевіряють удруге в інтеграційному тесті, а сценарій, який уже покриває API, не повторюють у браузері.

| Рівень      | Де                                 | Що перевіряє                                                                 | Запуск                                |
| ----------- | ---------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------- |
| Unit        | `backend/src/**/*.spec.ts`         | правила (`*.rules.ts`), сервіси з фейками портів, адаптери Google через HTTP | `npm test -w backend`                 |
| Unit        | `frontend/src/**/*.test.ts(x)`     | логіка фронтенду: помилки API, запити й інвалідація кешу, форми, дати        | `npm test -w frontend`                |
| Інтеграція  | `backend/test/*.int-spec.ts`       | увесь бекенд через HTTP на справжніх PostgreSQL і SeaweedFS                  | `npm run test:integration -w backend` |
| E2E         | `frontend/e2e/*.spec.ts`           | основні сценарії в браузері на зібраному Docker-стеку                        | `npm run e2e -w frontend`             |
| Архітектура | `backend/src/architecture.spec.ts` | межі модулів і відсутність циклів                                            | разом з unit-тестами бекенду          |

## Unit-тести

- **Бекенд.** Vitest. Сервіси отримують фейки портів у пам'яті: `FixedClock` замість `Clock`, записувач листів замість `MailTransport` тощо. Адаптери Google перевіряються по HTTP: `src/testing/google-http.ts` піднімає MSW для токенів, сертифікатів і Calendar API, а ID-токени підписує тестовим RSA-ключем, тож працює справжній `OAuth2Client`.
- **Фронтенд.** Vitest у jsdom (`src/test/setup.ts`). `src/test/api.tsx` підміняє `fetch` (`stubApi`) і рендерить хуки з `QueryClient` (`renderApiHook`), тож тест бачить і запит, і ключі кешу, які мутація інвалідує.
- **Покриття** — не менше 70% рядків, функцій, гілок і інструкцій (`test:cov`, збірка падає, якщо менше):
  - бекенд: увесь код, крім репозиторіїв, `*.store.ts` і контролерів (їх покривають інтеграційні тести), модулів Nest, `main.ts`, `app.setup.ts` і `openapi.ts`;
  - фронтенд: `features/**/*.ts` і `shared/{api,lib}`; компоненти перевіряють e2e-тести.

## Інтеграційні тести

- `test/setup/global-setup.ts` запускає PostgreSQL 18 і SeaweedFS у Testcontainers (потрібен Docker) і застосовує міграції з нуля. Замість контейнерів можна дати `INTEGRATION_DATABASE_URL` і `INTEGRATION_S3_ENDPOINT`.
- `createTestApp()` (`test/support/test-app.ts`) збирає застосунок так само, як `main.ts`, але з `FixedClock`, записувачем листів (`failNext()` імітує збій SMTP), сховищем, що вміє збоїти, і дешевим argon2. Google замінено на фейки з `test/support/calendar.ts` і `test/support/oauth.ts`.
- Перед кожним тестом `reset()` очищає всі таблиці; дані створюють фабрики з `test/support/factories.ts`, демо-дані не використовуються.
- Події після коміту доставляються явно: `deliverEvents()`. Періодичні задачі запускаються викликом, наприклад `app.get(ReminderJobs).run()`.
- Файли, що змінюють `process.env` до імпорту застосунку, повертають його в `afterAll`: усі файли працюють в одному процесі.

## E2E-тести

Playwright (Chromium) на Docker-стеку з nginx, тобто з тими самими заголовками безпеки, CSP і лімітами, що й у розгортанні. Сценарії:

1. Реєстрація → підтвердження email → група → задача → виконання.
2. Запрошення: людина без акаунта відкриває посилання, реєструється, підтверджує email, повертається до запрошення й приєднується.
3. Обмін задачами: учасник пропонує обмін, інший приймає, і задача переходить до нього.
4. П'ята невдала спроба входу блокує вхід навіть із правильним паролем.

- Сценарій, що перевіряється, іде через інтерфейс. Те, що йому передує (користувачі, групи, задачі), `e2e/support.ts` створює через API.
- Листи з посиланнями тести читають з Mailpit (`MAILPIT_URL`, типово `http://localhost:8025`).
- Кожен тест реєструє власних користувачів, тож тести незалежні й можуть іти паралельно на тій самій базі.
- Інтерфейс — англійською (ключ `errandly-locale` у `playwright.config.ts`), часовий пояс — `Europe/Kyiv`.
- Усі тести реєструються з однієї IP-адреси, тому стек запускається з більшим лімітом:

```bash
AUTH_RATE_LIMIT_PER_MINUTE=1000 docker compose up -d --build --wait
npm exec -w frontend -- playwright install chromium   # один раз
npm run e2e -w frontend                               # E2E_BASE_URL — інша адреса застосунку
```

## CI

`.github/workflows/ci.yaml` запускає на кожен PR і push у `main` паралельні джоби (спільне налаштування Node — `.github/actions/setup`):

| Джоб          | Кроки                                                                                                                      |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `lint`        | commitlint, Prettier, oxlint                                                                                               |
| `frontend`    | перевірка типів і типів CSS-модулів, unit-тести з покриттям, збірка                                                        |
| `backend`     | збірка, актуальність `openapi.json` і `schema.d.ts`, відповідність міграцій схемі, міграції й seed, unit-тести з покриттям |
| `integration` | інтеграційні тести                                                                                                         |
| `e2e`         | Docker-стек, smoke-тест `/api/health` і заголовки безпеки через nginx, Playwright; звіт і логи — якщо впало                |

Робочі процеси розділяються за тригером: розгортання матиме власний файл.
