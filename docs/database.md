# База даних

PostgreSQL 18, [Drizzle ORM](https://orm.drizzle.team) 0.45 і драйвер `pg`. Сутності та зв'язки описано в [domain.md](domain.md). Drizzle обрано за схему в TypeScript із повністю виведеними типами, нативний ESM без кодогенерації та читабельні SQL-міграції.

## Команди

```bash
docker compose up -d postgresql   # локальна база на :5432
npm run db:migrate                # застосувати міграції до DATABASE_URL
npm run db:seed                   # очистити всі таблиці й завантажити демо-дані (лише розробка й тести)
npm run db:generate               # після зміни схеми: нова міграція в backend/drizzle
npm run db:studio -w backend      # переглянути дані в браузері
npm run db:check -w backend       # перевірити узгодженість історії міграцій
```

## Де живе схема

Кожен модуль володіє своїми таблицями: `backend/src/<модуль>/<модуль>.schema.ts`. Файл `backend/src/db/schema.ts` збирає всі таблиці для drizzle-kit і типізованого `db.query`, а `db/relations.ts` описує зв'язки між ними. Зв'язки зібрано окремо, щоб файли схем не імпортували один одного по колу.

Запити до таблиці робить лише репозиторій модуля-власника (`<модуль>.repository.ts`). Інші модулі отримують ці дані через його публічне API ([architecture.md](architecture.md)). Зовнішні ключі між таблицями різних модулів дозволені: це моноліт з однією базою, і цілісність перевіряє PostgreSQL.

## Угоди

- **Імена:** у TypeScript — camelCase, у базі — snake_case (`casing: 'snake_case'`, без ручних назв колонок). Таблиці — множина (`tasks`). Обмеження: `<таблиця>_<суть>_key` для унікальних, `<таблиця>_<колонки>_idx` для індексів, `<таблиця>_<правило>` для `check`.
- **Ключі:** `uuid` з типовим значенням `uuidv7()`. UUIDv7 впорядковані за часом, тож індекси не фрагментуються. Функція є лише в PostgreSQL 18; Docker і CI використовують `postgres:18-alpine`.
- **Час:** лише `timestamptz` (UTC), а в часовому поясі користувача час показує фронтенд. Календарні дні без часу (відсутності) — `date`.
- **Переліки:** `pgEnum` зі значень `common/domain.ts`, тих самих, що в DTO.
- **Секрети:** токени (сесії, листи, запрошення) зберігаються лише як SHA-256, паролі — як argon2id, OAuth-токени календаря — зашифрованими.
- **Каскади:** дані, що не мають сенсу без власника, видаляються разом із ним (`cascade`): членство без групи, сесії без користувача. Посилання, які можуть «осиротіти», стають `set null`: виконавець задачі, автор групи. Бізнес-реакції (перерозподіл задач, коли учасник виходить) робить не каскад, а слухач події в тій самій транзакції.
- **Інваріанти в базі** там, де це просто: унікальність, `check` для діапазонів (складність 1–5, `starts_on ≤ ends_on`, дні тижня 1–7). Складні правила (`LAST_ADMIN`) перевіряють сервіси.

## Міграції

- Схема — у TypeScript, міграції — згенеровані SQL-файли в `backend/drizzle/`. Їх комітять разом зі зміною схеми.
- **Злиту міграцію не редагують:** будь-яка зміна — це нова міграція. CI запускає `db:generate` і падає, якщо схема й міграції розійшлися.
- Перед злиттям перегляньте згенерований SQL: drizzle-kit може запропонувати видалити й створити колонку замість перейменування.
- Застосування: `npm run db:migrate` локально (tsx) і одноразовий сервіс `migrate` у Docker (`node backend/dist/db/migrate.js`) перед стартом бекенду.

## Демо-дані

`npm run db:seed` очищає **всі** таблиці (`TRUNCATE … CASCADE`) і завантажує ті самі дані, що й мок-API фронтенду: 4 користувачі, групи «Room 12» і «Podil Flat», задачі за 2 тижні назад і 4 вперед, сповіщення. Вхід — `anya@errandly.dev` / `Pass1234`.

- Лише для розробки й тестів: з `NODE_ENV=production` команда відмовляється працювати. Seed ніколи не входить у міграції й не запускається під час старту.
- Дані будуються чистою функцією `buildSeed(now)` (`db/seed-data.ts`) з unit-тестами. Таблиці для очищення seed знаходить у схемі сам, тож нова таблиця не забудеться.

## Реєстр подій

`event_publications` — технічна таблиця шини подій: рядок на кожного слухача після коміту, з кількістю спроб, часом наступної спроби й останньою помилкою. Виконані рядки можна періодично видаляти; ті, на яких слухач здався (`completed_at` і `next_attempt_at` порожні), варто переглядати. Механізм описано в [architecture.md](architecture.md#події).

## Тести з базою

- Unit-тести (`*.spec.ts`) базу не використовують: репозиторії й порти підміняються фейками.
- E2E (`test/*.e2e-spec.ts`): `test/setup/global-setup.ts` піднімає через Testcontainers один PostgreSQL 18 на запуск і застосовує міграції з нуля. Потрібен запущений Docker; `E2E_DATABASE_URL` натомість вказує на наявну базу (її таблиці буде очищено).
- `test/support/test-app.ts` (`createTestApp`) запускає весь `AppModule` з `FixedClock`, `RecordingMailTransport` (записує листи, `failNext()` імітує збій SMTP) і швидким argon2. `reset()` очищає всі таблиці (`db/tables.ts#truncateAll`) перед кожним тестом, `deliverEvents()` доставляє події після коміту.
- Дані створюють фабрики з `test/support/factories.ts` (`createUser`, `signIn`). Тести не покладаються на демо-дані.
